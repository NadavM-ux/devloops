בדיקת הרשאות בשרת

Enforce server-side auth

הסתרתם כפתור או דף של אדמין? זה עדיין לא מגן. כל אחד יכול לשלוח בקשה ישר לשרת, בלי לעבור דרך המסך. ב-Base44, פלטפורמת הווייב-קודינג שוויקס קנתה, היו נקודות קצה נסתרות שהספיק להן מזהה של אפליקציה כדי להירשם לאפליקציות פרטיות. החוקרים של Wiz דיווחו, הפרצה נסגרה תוך פחות מ-24 שעות, ולפי Wix אף אחד לא ניצל אותה.

ההוראה לקלוד
לפני שאנחנו מעלים את האפליקציה, תעבור על כל נקודת קצה בשרת: API routes, server actions, edge functions, ופונקציות במסד הנתונים שאפשר לקרוא להן מהדפדפן (RPC). 1. תוודא שכל אחת מזהה בשרת מי המשתמש (מאמתת את הסשן או את ה-JWT) לפני שהיא עושה משהו, גם אם הכפתור או הדף שמובילים אליה מוסתרים במסך. 2. תוודא שהיא גם בודקת מה מותר לו: תפקיד, בעלות, מנוי. לפי מידע מהשרת או ממסד הנתונים, אף פעם לא לפי מה שהדפדפן שלח (role, isAdmin או userId בגוף הבקשה לא נחשבים). 3. בדיקה בצד הלקוח היא רק לתצוגה. פעולות של אדמין, תשלומים וכל מה שעולה כסף רצים רק בשרת, עם בדיקה בתוך הפונקציה עצמה. middleware לבד לא מספיק. 4. ברירת המחדל היא חסימה: נקודת קצה בלי בדיקה מחזירה 401 ולא נשארת פתוחה. פונקציות security definer במסד הנתונים בודקות את auth.uid() בעצמן. 5. תכתוב טסט שקורא לכל נקודת קצה פעם בלי התחברות ופעם עם משתמש רגיל, ומוודא שמקבלים 401 או 403 בכל מקום שצריך. לפני שאתה משנה משהו, תראה לי טבלה: נקודת קצה, מי אמור לגשת אליה, ומה היא בודקת היום.
Before we launch, go through every server endpoint: API routes, server actions, edge functions, and database functions the browser can call (RPC). 1. Make sure each one identifies the user on the server (verifies the session or JWT) before it does anything, even if the button or page that leads to it is hidden in the UI. 2. Make sure it also checks what the user is allowed to do: role, ownership, subscription. Based on server or database data, never on what the browser sent (role, isAdmin or userId in the request body don't count). 3. Client-side checks are for display only. Admin actions, payments and anything that costs money run only on the server, with the check inside the function itself. Middleware alone isn't enough. 4. Deny by default: an endpoint without a check returns 401 instead of staying open. security definer database functions check auth.uid() themselves. 5. Write a test that calls every endpoint once logged out and once as a regular user, and confirms a 401 or 403 everywhere it should. Before you change anything, show me a table: endpoint, who should reach it, and what it checks today.

איך בודקים מבקשים מ-Claude להריץ את הטסט מסעיף 5 ולהראות את התוצאות: בלי התחברות, כל נקודת קצה פרטית מחזירה 401, ומשתמש רגיל שמנסה פעולה של אדמין מקבל 403.

לחסום שינוי של שדות

Block field tampering

השרת לא אמור לשמור כל מה שהדפדפן שולח. אחרת משתמש מוסיף לבקשה שדה שלא היה בטופס, כמו role: "admin" או credits: 99999, והשרת פשוט שומר. ככה ב-2012 מישהו קיבל גישת אדמין לפרויקטים בגיטהאב, כולל Ruby on Rails.

ההוראה לקלוד
תמצא כל מקום שבו נוצרת או מתעדכנת רשומה לפי מה שהגיע מהדפדפן: טפסים, API routes, server actions, וכל insert או update שהדפדפן עושה ישירות במסד הנתונים. 1. לכל פעולה תגדיר רשימה סגורה של שדות שהמשתמש רשאי לשנות, עם סכמה (למשל zod) שזורקת כל שדה אחר. אף פעם לא להעביר את req.body או אובייקט שלם ישר למסד הנתונים. 2. שדות כמו role, is_admin, plan, credits, balance, price, user_id, owner_id, email_verified ו-created_at נקבעים רק בשרת, אף פעם לא מהבקשה. 3. מחירים וסכומים מחושבים בשרת לפי המוצר, לא לפי מה שהדפדפן שלח. 4. אם הדפדפן כותב ישירות ל-Supabase: תעביר תפקידים והרשאות לטבלה נפרדת שמשתמשים לא יכולים לכתוב אליה, או תבטל את הרשאת ה-update על הטבלה מ-authenticated ותיתן אותה רק על העמודות המותרות. 5. תכתוב טסט ששולח עדכון עם role: "admin" ועם user_id של משתמש אחר, ומוודא שהם לא נשמרים. לפני שאתה משנה משהו, תראה לי לכל טבלה אילו שדות יהיו מותרים לשינוי.
Find every place where a record is created or updated from what the browser sent: forms, API routes, server actions, and any insert or update the browser runs directly against the database. 1. For each action, define a closed list of fields the user may change, with a schema (for example zod) that drops everything else. Never pass req.body or a whole object straight to the database. 2. Fields like role, is_admin, plan, credits, balance, price, user_id, owner_id, email_verified and created_at are set only on the server, never from the request. 3. Prices and totals are calculated on the server from the product, not taken from what the browser sent. 4. If the browser writes to Supabase directly: move roles and permissions to a separate table users can't write to, or revoke the table-level update privilege from authenticated and grant update only on the allowed columns. 5. Write a test that sends an update with role: "admin" and another user's user_id, and confirms neither is saved. Before you change anything, show me which fields will be writable for each table.

איך בודקים מבקשים מ-Claude לשלוח עדכון פרופיל עם role: "admin", עם credits גבוה ועם user_id של משתמש אחר, ולהראות שאף אחד מהם לא נשמר.

קוקיז מאובטחים לסשן

Secure session cookies

הקוקי של הסשן הוא בעצם המפתח לחשבון: מי שמחזיק אותו נכנס בלי סיסמה ובלי קוד אימות. ככה ב-2023 נגנבו שלושת ערוצי היוטיוב של Linus Tech Tips, הגדול שבהם עם יותר מ-15 מיליון מנויים. אי אפשר למנוע כל גניבה, אבל אפשר לנעול את הקוקי ולקצר מאוד את הזמן שקוקי גנוב עובד.

ההוראה לקלוד
תבדוק איך האפליקציה שומרת את הסשן של המשתמשים. 1. אם אנחנו מנהלים סשן בעצמנו: קוקי עם HttpOnly, Secure, SameSite=Lax (או Strict כשאפשר) ו-Path=/, בלי Domain רחב מדי. לא ב-localStorage ולא ב-sessionStorage. 2. אם ספריית ההתחברות צריכה שהדפדפן יקרא את הטוקן (כמו הלקוח של Supabase), אל תשבור אותה. תגיד לי, ובמקום זה תוודא תוקף קצר לטוקן, רוטציה ל-refresh token, ו-Content-Security-Policy קפדני שמקשה על XSS. 3. תוקף קצר לסשן, וניתוק אחרי זמן בלי פעילות. 4. מזהה סשן חדש בכל התחברות. שינוי של סיסמה, אימייל או הרשאות מבטל את כל הסשנים האחרים. 5. יציאה מבטלת את הסשן בשרת, לא רק מוחקת את הקוקי. 6. אם בקשות שמשנות מידע מסתמכות על קוקי, תוסיף הגנת CSRF (טוקן, או בדיקה של Origin). 7. האתר עובד רק ב-HTTPS, עם HSTS. לפני שאתה משנה משהו, תראה לי איפה הטוקן נשמר היום ומה ההגדרות שלו.
Check how the app stores user sessions. 1. If we manage sessions ourselves: a cookie with HttpOnly, Secure, SameSite=Lax (or Strict where possible) and Path=/, without an overly broad Domain. Not in localStorage or sessionStorage. 2. If our auth library needs the browser to read the token (like the Supabase client), don't break it. Tell me, and instead make sure tokens are short-lived, refresh tokens rotate, and a strict Content-Security-Policy makes XSS harder. 3. A short session lifetime, and sign-out after a period of inactivity. 4. A new session ID on every login. Changing the password, email or permissions revokes all other sessions. 5. Logging out revokes the session on the server, not just the cookie. 6. If state-changing requests rely on a cookie, add CSRF protection (a token, or an Origin check). 7. The site runs on HTTPS only, with HSTS. Before you change anything, show me where the token is stored today and with which settings.

איך בודקים פותחים את האתר במחשב, לוחצים F12, ובלשונית Application נכנסים ל-Cookies. ליד קוקי הסשן צריך לראות סימון ב-HttpOnly וב-Secure, ו-SameSite על Lax או Strict. ב-Supabase הדפדפן קורא את הטוקן בכוונה, ואז בודקים תוקף קצר ו-CSP.

hash לסיסמאות

Hash passwords

סיסמה אף פעם לא נשמרת כמו שהיא, וגם לא בהצפנה שאפשר לפתוח. שומרים רק hash: טביעת אצבע חד-כיוונית שאי אפשר להפוך בחזרה לסיסמה. Meta שמרה סיסמאות של מאות מיליוני משתמשים בטקסט קריא, כולל מיליוני משתמשי אינסטגרם, ובספטמבר 2024 הרגולטור האירי קנס אותה ב-91 מיליון יורו.

ההוראה לקלוד
תבדוק איך האפליקציה שומרת סיסמאות. 1. אם ההתחברות עוברת דרך שירות (Supabase Auth, Clerk, Firebase, Auth0), תוודא שאין אצלנו שום טבלה, עמודה או לוג ששומרים סיסמאות, ותעצור כאן. 2. אם אנחנו שומרים סיסמאות בעצמנו: hash עם Argon2id (לפחות 19 MiB זיכרון ו-2 איטרציות, לפי OWASP) דרך ספרייה מוכרת, עם salt אקראי לכל משתמש. אם אין Argon2id, אז bcrypt עם cost 12 (שים לב שהוא מתעלם מכל מה שאחרי 72 בייטים). לא MD5, לא SHA-256 לבד, ולא הצפנה הפיכה. 3. בדיקה בהתחברות רק דרך פונקציית ה-verify של הספרייה. 4. סיסמאות לא נכתבות לשום מקום: לא ללוגים, לא להודעות שגיאה, לא לאנליטיקס, והן אף פעם לא חוזרות בתשובות של ה-API. 5. אם יש סיסמאות ישנות בטקסט קריא או ב-hash חלש, תכתוב תוכנית מעבר: hash מחדש בהתחברות הבאה, ואיפוס סיסמה למי שלא נכנס. 6. הגבלת קצב לניסיונות התחברות, ובדיקה של סיסמאות חדשות מול רשימת סיסמאות שדלפו. לפי NIST, לפחות 15 תווים כשאין אימות דו-שלבי. לפני שאתה משנה משהו, תראה לי איפה ואיך סיסמאות נשמרות היום.
Check how the app stores passwords. 1. If login goes through a service (Supabase Auth, Clerk, Firebase, Auth0), make sure no table, column or log of ours stores passwords, and stop here. 2. If we store passwords ourselves: hash them with Argon2id (at least 19 MiB of memory and 2 iterations, per OWASP) through a well-known library, with a random salt per user. If Argon2id isn't available, use bcrypt with cost 12 (note that it ignores everything after 72 bytes). No MD5, no plain SHA-256, and no reversible encryption. 3. Check logins only through the library's verify function. 4. Passwords are never written anywhere: not to logs, error messages or analytics, and never returned by the API. 5. If old passwords exist in readable form or with a weak hash, write a migration plan: re-hash on the next login, and force a reset for users who don't log in. 6. Rate-limit login attempts, and check new passwords against a list of leaked passwords. Per NIST, at least 15 characters when there's no second factor. Before you change anything, show me where and how passwords are stored today.

איך בודקים פותחים את טבלת המשתמשים. בעמודת הסיסמה צריך לראות משהו שמתחיל ב-$argon2id$ או ב-$2b$, אף פעם לא סיסמה שאפשר לקרוא. אם ההתחברות עוברת דרך Supabase Auth או Clerk, הסיסמאות בכלל לא בטבלאות שלכם, וזה בדיוק מה שרוצים.

לנעול גישה לרשומות

Lock record access

רואים מזהה בכתובת או בבקשה, כמו /orders/1043? מישהו ינסה 1042. אם השרת לא בודק שהרשומה שייכת למי שביקש, הוא יקבל רשומה של מישהו אחר. ככה ב-2025 חוקרים הורידו ב-1 את המספר של מועמד ב-McHire, מערכת הגיוס של מקדונלדס, וגילו שהם יכולים להגיע למידע של יותר מ-64 מיליון מועמדים. לממשק הניהול הם נכנסו עם הסיסמה 123456.

ההוראה לקלוד
תמצא כל מקום שבו קוראים, משנים או מוחקים רשומה לפי מזהה שהגיע מהבקשה: נתיבים כמו /api/orders/[id], פרמטרים בכתובת, server actions, הורדת קבצים וקישורים לקבצים. 1. כל שאילתה מסננת גם לפי הבעלים, לא רק לפי ה-id (למשל where id = $1 and user_id = $2), כשה-user_id מגיע מהסשן בשרת ולא מהבקשה. 2. אם המידע ב-Supabase: RLS עם policy של auth.uid() על כל טבלה כזאת, וכל קוד שרת שעובד עם service_role בודק בעלות בעצמו, כי המפתח הזה עוקף את ה-RLS. 3. רשומה שלא שייכת למשתמש מחזירה 404, כדי לא לגלות שהיא קיימת. 4. מזהים שאי אפשר לנחש (UUID) במקום מספרים רצים, אבל רק כשכבה נוספת, לא במקום הבדיקה. 5. קבצים פרטיים נפתחים רק דרך קישור חתום עם תוקף קצר, אחרי בדיקת בעלות. 6. תכתוב טסט עם שני משתמשים: משתמש א' מנסה לקרוא, לשנות ולמחוק רשומה של משתמש ב', וכל ניסיון נחסם. לפני שאתה משנה משהו, תראה לי רשימה של כל הגישות לפי מזהה, ומה כל אחת בודקת היום.
Find every place where a record is read, changed or deleted by an ID that came from the request: routes like /api/orders/[id], URL parameters, server actions, file downloads and file links. 1. Every query also filters by owner, not just by id (for example where id = $1 and user_id = $2), with user_id taken from the server-side session, never from the request. 2. If the data is in Supabase: RLS with an auth.uid() policy on every such table, and any server code that uses service_role checks ownership itself, because that key bypasses RLS. 3. A record that doesn't belong to the user returns 404, so you don't reveal that it exists. 4. Use IDs that can't be guessed (UUIDs) instead of sequential numbers, but only as an extra layer, never instead of the check. 5. Private files open only through a short-lived signed link, after an ownership check. 6. Write a test with two users: user A tries to read, change and delete user B's record, and every attempt is blocked. Before you change anything, show me a list of every access by ID and what each one checks today.

איך בודקים נכנסים עם שני משתמשים בשני דפדפנים (או אחד בחלון גלישה בסתר). לוקחים מזהה של רשומה של משתמש א׳ ומנסים לפתוח, לשנות ולמחוק אותה ממשתמש ב׳. כל ניסיון צריך להיכשל.

כל החמש בהודעה אחת

גרסה מקוצרת של כל ההוראות. Claude יעבור עליהן לפי הסדר, ויבקש אישור לפני כל דבר שאי אפשר להחזיר.

הצגת הטקסט המלא
אנחנו עומדים להעלות את האפליקציה. תעבוד כמו מהנדס אבטחה בכיר, ותבדוק את הפרויקט ב-5 דברים, אחד אחרי השני: 1. הרשאות בשרת: כל נקודת קצה (API routes, server actions, edge functions, RPC) בודקת בשרת מי המשתמש ומה מותר לו, גם אם הכפתור מוסתר במסך. לא סומכים על role או userId שהגיעו מהדפדפן. ברירת המחדל היא חסימה. 2. שדות: לכל יצירה ועדכון של רשומה יש רשימה סגורה של שדות מותרים (סכמה שזורקת את כל השאר). role, plan, credits, price ו-user_id נקבעים רק בשרת. 3. סשן: קוקי עם HttpOnly, Secure ו-SameSite=Lax, תוקף קצר, מזהה חדש בכל התחברות, יציאה שמבטלת את הסשן בשרת, והגנת CSRF. אם ספריית ההתחברות צריכה שהדפדפן יקרא את הטוקן: תוקף קצר, רוטציה ו-CSP קפדני. 4. סיסמאות: רק hash עם Argon2id (או bcrypt עם cost 12) דרך ספרייה מוכרת, אף פעם לא טקסט קריא או הצפנה הפיכה, ושום סיסמה בלוגים. אם ההתחברות עוברת דרך שירות כמו Supabase Auth, תוודא שאין אצלנו סיסמאות בכלל. 5. גישה לרשומות: כל שאילתה לפי מזהה מסננת גם לפי המשתמש מהסשן (או RLS עם auth.uid()), רשומה של מישהו אחר מחזירה 404, וקבצים פרטיים נפתחים רק בקישור חתום. על כל אחד: תראה לי מה מצאת, תתקן, ותראה איך בדקת. לפני כל דבר שאי אפשר להחזיר אחורה, תשאל אותי.
We're about to launch this app. Work like a senior security engineer and check the project for these 5 things, one at a time: 1. Server-side auth: every endpoint (API routes, server actions, edge functions, RPC) checks on the server who the user is and what they're allowed to do, even when the button is hidden in the UI. Never trust a role or userId sent by the browser. Deny by default. 2. Fields: every create and update has a closed list of allowed fields (a schema that drops the rest). role, plan, credits, price and user_id are set only on the server. 3. Sessions: a cookie with HttpOnly, Secure and SameSite=Lax, a short lifetime, a new ID on every login, logout that revokes the session on the server, and CSRF protection. If the auth library needs the browser to read the token: short-lived tokens, rotation and a strict CSP. 4. Passwords: only a hash with Argon2id (or bcrypt with cost 12) through a well-known library, never readable text or reversible encryption, and no password in logs. If login goes through a service like Supabase Auth, make sure we store no passwords at all. 5. Record access: every query by ID also filters by the user from the session (or RLS with auth.uid()), another user's record returns 404, and private files open only through signed links. For each one: show me what you found, fix it, and show me how you checked it. Ask me before anything that can't be undone.
