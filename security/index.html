01

להסתיר את המפתחות

Hide API keys

מפתח API זה כמו כרטיס אשראי. אם הוא נמצא בקוד של האתר, כל מי שנכנס יכול להעתיק אותו, ואתם משלמים על מה שהוא עושה איתו. המקום של מפתחות כאלה הוא רק בשרת.

ההוראה לקלוד
לפני שאנחנו מעלים את האפליקציה, תמצא כל סוד שיש בפרויקט: מפתחות API, טוקנים, סיסמאות ו-connection strings (למשל sk-..., sk_live_..., service_role). 1. תוודא שאף אחד מהם לא נמצא בקוד שרץ בדפדפן, או במשתני סביבה שנכנסים לקוד של הדפדפן (NEXT_PUBLIC_, VITE_, EXPO_PUBLIC_, REACT_APP_). 2. תעביר את כל הסודות למשתני סביבה בשרת, ותעשה את הקריאות שצריכות אותם מ-API route או מ-edge function. 3. תוודא ש-.env נמצא ב-.gitignore, ותוסיף קובץ .env.example עם ערכים לדוגמה. 4. תחפש מפתחות שנשארו בקוד של ה-build שעולה לאוויר. לפני שאתה משנה משהו, תראה לי רשימה של מה מצאת ואיפה.
Before we launch, find every secret in this project: API keys, tokens, passwords and connection strings (for example sk-..., sk_live_..., service_role). 1. Make sure none of them is in code that runs in the browser, or in env vars that get bundled into it (NEXT_PUBLIC_, VITE_, EXPO_PUBLIC_, REACT_APP_). 2. Move every secret to server-side env vars, and make the calls that need them from an API route or an edge function. 3. Make sure .env is in .gitignore, and add a .env.example file with placeholder values. 4. Search the production build for any key that's left. Before you change anything, show me a list of what you found and where.

איך בודקים פותחים את האתר במחשב, לוחצים F12, ומחפשים בלשונית Sources את sk- ואת secret. לא אמור להופיע שום מפתח סודי.

02

לנקות את ההיסטוריה

Purge Git secrets

מחקתם מפתח מהקוד? הוא עדיין שמור בגרסאות הקודמות בגיטהאב. בניסוי של Comparitech, בוטים מצאו מפתח שדלף לגיטהאב תוך דקה. אז קודם מחליפים את המפתח, ורק אחרי זה מנקים את ההיסטוריה.

ההוראה לקלוד
תסרוק את כל היסטוריית ה-git של הריפו ותחפש סודות, לא רק בגרסה הנוכחית. תשתמש ב-gitleaks או ב-trufflehog. על כל סוד שתמצא: 1. תגיד לי איזה מפתח זה, ואיפה מבטלים אותו ויוצרים חדש. קודם מחליפים, כי מפתח שעלה פעם לגיטהאב צריך להיחשב כאילו כבר דלף. 2. אחרי שאאשר שהמפתחות החדשים במקום, תמחק את הישנים מההיסטוריה עם git filter-repo. לפני זה תעשה גיבוי של הריפו. 3. תשאל אותי לפני כל force push. 4. תוסיף סריקת סודות שרצה לפני כל commit, כדי שזה לא יקרה שוב.
Scan this repo's entire git history for secrets, not just the current files. Use gitleaks or trufflehog. For every secret you find: 1. Tell me which key it is and where I revoke it and create a new one. Rotate first, because a key that was ever pushed should be treated as leaked. 2. Once I confirm the new keys are in place, remove the old ones from history with git filter-repo. Back up the repo first. 3. Ask me before any force push. 4. Add a secret scan that runs before every commit, so this can't happen again.

איך בודקים מריצים שוב את הסריקה על כל ההיסטוריה. צריך לצאת 0 ממצאים, והמפתחות הישנים צריכים להיות מבוטלים אצל הספק.

03

רק המפתח הציבורי

Use public DB key

בסופבייס יש שני סוגים של מפתחות. הציבורי (publishable, או anon בגרסה הישנה) מותר שיהיה באתר. הסודי (secret, או service_role) עוקף את כל ההגנות. אם הוא מגיע לאתר, כל אחד יכול למחוק לכם הכל.

ההוראה לקלוד
תבדוק אילו מפתחות של מסד הנתונים מגיעים לדפדפן. שם מותר רק המפתח הציבורי (בסופבייס: anon או sb_publishable_...). המפתח הסודי (service_role או sb_secret_...) עוקף את ה-Row Level Security, אז הוא חייב להיות רק בשרת: לא בקוד של האתר ולא במשתנה סביבה ציבורי. אם המפתח הסודי הגיע פעם לדפדפן או לגיטהאב, תגיד לי להחליף אותו, ותעביר כל פעולה שצריכה אותו לפונקציה בשרת שבודקת קודם מי המשתמש ומה מותר לו.
Check which database keys reach the browser. Only the public key is allowed there (in Supabase: the anon or sb_publishable_... key). The secret key (service_role or sb_secret_...) bypasses Row Level Security, so it must stay on the server: never in client code and never in a public env var. If the secret key ever reached the browser or GitHub, tell me to rotate it, and move every operation that needs it into a server function that first checks who the user is and what they're allowed to do.

איך בודקים לוחצים F12, פותחים את Network, בוחרים בקשה לסופבייס ומסתכלים על הכותרת apikey. היא צריכה להתחיל ב-sb_publishable_, או להיות מפתח ה-anon מהדשבורד.

04

להפעיל RLS

Enable row-level security

RLS זה מה שדואג שכל משתמש יראה רק את המידע שלו. בלי זה, גם המפתח הציבורי פותח הכל. ככה דלפו מיליון וחצי מפתחות API במולטבוק.

ההוראה לקלוד
תפעיל Row Level Security על כל טבלה בסכמה public, ותכתוב policies כך שכל משתמש יוכל לקרוא ולשנות רק את השורות שלו (למשל auth.uid() = user_id). כללים: - בלי using (true) או with check (true) על insert, update או delete. - מידע שבאמת ציבורי מקבל policy של קריאה בלבד, וזהו. - פעולות של אדמין רצות בשרת, לא מהדפדפן. אחרי זה תוכיח שזה עובד: תנסה לקרוא ולשנות שורות של משתמש אחר, פעם בלי להתחבר ופעם מחובר כמשתמש אחר. כל ניסיון צריך לחזור ריק או להיחסם. תראה לי את התוצאות לכל טבלה.
Turn on Row Level Security for every table in the public schema, and write policies so each user can only read and change their own rows (for example auth.uid() = user_id). Rules: - No using (true) or with check (true) on insert, update or delete. - Data that's really public gets a read-only policy, and nothing more. - Admin actions run on the server, not from the browser. Then prove it works: try to read and change another user's rows, once with no login and once signed in as a different user. Every attempt should come back empty or be blocked. Show me the results for each table.

איך בודקים בדשבורד של סופבייס פותחים את Security Advisor. לא אמורה להופיע אף אזהרה על RLS.

05

להצפין מידע רגיש

Encrypt sensitive data

תעודות זהות, טלפונים, הודעות פרטיות. אם מישהו בכל זאת נכנס למסד הנתונים, שיראה ג׳יבריש ולא את המידע. במולטבוק ההודעות הפרטיות נשמרו בלי הצפנה.

סיסמאות זה סיפור אחר. להן עושים hash ולא הצפנה, ועל זה נדבר בחלק 2.

ההוראה לקלוד
תמצא כל שדה ששומר מידע אישי רגיש: תעודות זהות, טלפונים, כתובות, הודעות פרטיות, פרטי בריאות או תשלום, וטוקנים של שירותים אחרים. 1. תצפין את השדות האלה באפליקציה לפני שהם נשמרים, עם AES-256-GCM ו-IV אקראי לכל ערך. 2. תשמור את מפתח ההצפנה כסוד בשרת (משתנה סביבה או secret manager), אף פעם לא במסד הנתונים, בריפו או בדפדפן. 3. תוודא שהערכים האלה לא מופיעים בלוגים, בהודעות שגיאה או בכלי אנליטיקס. 4. תוודא שכל התקשורת עוברת רק ב-HTTPS. אם צריך לחפש לפי אחד השדות, תשמור לידו hash עם מפתח (HMAC) בשביל החיפוש. את השמירה של הסיסמאות לא משנים בשלב הזה. לפני שאתה מריץ משהו, תכתוב תוכנית מעבר לשורות שכבר קיימות ותראה לי אותה.
Find every field that stores sensitive personal data: ID numbers, phone numbers, addresses, private messages, health or payment details, and tokens for other services. 1. Encrypt these fields in the app before they're saved, with AES-256-GCM and a random IV for every value. 2. Keep the encryption key as a server-side secret (env var or secret manager), never in the database, the repo or the browser. 3. Make sure these values never show up in logs, error messages or analytics. 4. Make sure all traffic goes over HTTPS only. If we need to search by one of these fields, store a keyed hash (HMAC) next to it for lookups. Don't change how passwords are stored in this step. Before you run anything, write a migration plan for the existing rows and show it to me.

איך בודקים פותחים את הטבלה בדשבורד. בשדות הרגישים צריך לראות ג׳יבריש, לא תעודת זהות או מספר טלפון.

כל החמש בהודעה אחת

גרסה מקוצרת של כל ההוראות. Claude יעבור עליהן לפי הסדר, ויבקש אישור לפני כל דבר שאי אפשר להחזיר.

הצגת הטקסט המלא
אנחנו עומדים להעלות את האפליקציה. תעבוד כמו מהנדס אבטחה בכיר, ותבדוק את הפרויקט ב-5 דברים, אחד אחרי השני: 1. מפתחות וסודות: אף אחד לא בקוד של הדפדפן או במשתני סביבה ציבוריים (NEXT_PUBLIC_, VITE_ וכו'). כולם בשרת, ו-.env נמצא ב-.gitignore. 2. היסטוריית git: תסרוק את כל ההיסטוריה עם gitleaks או trufflehog, ותגיד לי אילו מפתחות להחליף. אחרי שאחליף, תנקה את ההיסטוריה עם git filter-repo (קודם גיבוי, ותשאל לפני force push), ותוסיף סריקה לפני כל commit. 3. מפתחות של מסד הנתונים: בדפדפן רק המפתח הציבורי (anon או sb_publishable_...). המפתח הסודי (service_role או sb_secret_...) רק בשרת. 4. Row Level Security על כל טבלה, עם policies שכל משתמש רואה ומשנה רק את השורות שלו. בלי using (true) על כתיבה. תוכיח את זה: תנסה לקרוא נתונים של משתמש אחר עם המפתח הציבורי. 5. שדות רגישים (תעודות זהות, טלפונים, הודעות פרטיות) מוצפנים עם AES-256-GCM לפני השמירה, המפתח שמור בשרת, ושום דבר מהם לא נכתב ללוגים. על כל אחד: תראה לי מה מצאת, תתקן, ותראה איך בדקת. לפני כל דבר שאי אפשר להחזיר אחורה, תשאל אותי.
We're about to launch this app. Work like a senior security engineer and check the project for these 5 things, one at a time: 1. Keys and secrets: none in browser code or public env vars (NEXT_PUBLIC_, VITE_, etc.). All of them on the server, and .env in .gitignore. 2. Git history: scan all of it with gitleaks or trufflehog and tell me which keys to rotate. After I rotate them, clean the history with git filter-repo (back up first, ask before any force push), and add a scan that runs before every commit. 3. Database keys: only the public key in the browser (anon or sb_publishable_...). The secret key (service_role or sb_secret_...) only on the server. 4. Row Level Security on every table, with policies so each user only sees and changes their own rows. No using (true) on writes. Prove it: try to read another user's data with the public key. 5. Sensitive fields (ID numbers, phone numbers, private messages) encrypted with AES-256-GCM before they're saved, the key kept on the server, and none of them written to logs. For each one: show me what you found, fix it, and show me how you checked it. Ask me before anything that can't be undone.
